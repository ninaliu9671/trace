### Task 2：更新汇报框架对话策略（A/B/C 三条路径）

**Files:**
- Modify: `lib/prompts.ts:61-69`（汇报框架段落）

- [ ] **Step 1: 替换汇报框架对话策略**

  将当前 `▸ 汇报框架` 的 `对话策略` 部分：

  ```
  对话策略：
  - 已有框架内容作为基础，问用户是要新建还是调整
  - 从最高层级（年报/述职）往下问到日常记录
  - 每层确认：名称、触发时机、汇报对象、包含模块
  - 节点数量通常 3-6 个，子节点 parent_id 填父节点的 name
  ```

  替换为：

  ```
  对话策略：
  - 首先询问用户当前情况，选择路径：
    「接下来我们来梳理你的汇报框架。你现在的情况是哪种？
    A. 公司有固定模板，我想严格按这个来
    B. 我有自己的框架，但想看看能不能更完善
    C. 我没有固定框架，帮我建一套」

  【路径 A：适配现有模板】
  - 请用户上传或描述现有模板结构
  - 按模板框架填入对应内容
  - 如发现明显缺失，单独提示：「我注意到你的模板里没有涉及[XX]，根据你的工作内容，这部分可能会有用，要加进去吗？」

  【路径 B：优化已有框架】
  - 请用户描述或上传现有框架
  - 对照职业档案做 gap 分析，输出：
    「你现有框架的覆盖情况：✓ 已覆盖：[列出] △ 可以补充：[列出 3-5 条建议，说明为什么]」
  - 让用户选择是否采纳每条建议，整合成最终框架

  【路径 C：从头新建】
  - 根据职业档案自动生成汇报框架
  - 覆盖：周期性报告（周报/月报/季报/年报）、项目报告、述职报告（如适用）、专项报告（如适用）
  - 每种报告列出框架维度及向下拆解逻辑

  - 节点数量通常 3-6 个，子节点 parent_id 填父节点的 name
  ```

### Task 3：更新记录维度生成策略（固定骨架 + 条件维度 + 职业特异性）

  - 优先读取已有的汇报框架，从框架模块倒推维度

  替换为：

  ```
  对话策略：
  - 优先读取已有的汇报框架，从框架模块倒推维度
  - 结合用户职位，提出维度建议，让用户确认或调整
  - 维度名称结合用户实际职位，不用「工作进展」这类通用词
  - 最小层级的 prompt_text 要有引导性，像了解情况的同事在追问
  - 控制总维度数量在 8-10 个以内，合并高度相似的维度

  【维度生成框架】

  第一步：分析职业特征
  - 核心工作类型（执行类/管理类/创作类/分析类/销售类）
  - 主要工作场景（项目制/流程制/客户制/内容制）
  - 是否有下属（决定是否加入团队管理维度）
  - 行业合规要求（决定是否加入合规维度）

  第二步：套用维度框架

  固定骨架（所有职业都有）：
  - 跨部门/跨角色协作
  - 系统与工具
  - 指标与目标
  - 学习与积累

  条件维度（按职业画像判断是否加入）：
  - 团队管理：有下属时加入
  - 合规与风控：金融/医疗/法律/教育等强监管行业加入
  - 客户管理：销售/客服/客户成功类职业加入
  - 内容/产品：内容运营/产品经理类职业加入

  职业特异性维度（根据核心职责动态生成）：
  - 拆解用户的 3-5 条核心职责
  - 每条职责转化为 1-2 个日志维度
  - 合并高度相似的维度，控制总数在 8-10 个以内
  ```
